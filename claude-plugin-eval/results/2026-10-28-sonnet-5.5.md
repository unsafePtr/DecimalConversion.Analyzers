# Eval of the dotnet11-floating-point skill, Sonnet 5.5, 2026-10-28

This run measures the skill as it ships now, with the package it carries, on a fixture with one site more.
The new site is a constant with 17 significant digits, `(decimal)(1.0 / 8760)`, whose .NET 10 value the 15-digit `G15` recipe misses by one unit in the last digit.
With the skill the agent took the analyzer and `dotnet format` path in every run that changed code, kept every site it should keep, and got the new site right at no extra cost.
Without the skill every run also got it right, but two of nine had to find out that the `G15` recipe fails its test and wrote their own port of .NET 10's conversion, at more than twice the usual cost.

The raw result, with every grader verdict and each run's final message, is [2026-10-28-sonnet-5.5.json](2026-10-28-sonnet-5.5.json).

## What changed since the last run

- The skill adds the plugin's own copy of the package as a restore source, through `RestoreAdditionalProjectSources`, so a migration needs no feed.
- The command that lists the sites keeps file paths with spaces, and makes them relative on Windows.
- The package is 1.3.2, whose DCV002 fix writes the literal .NET 10 folded, from a port of its conversion; 1.3.0 wrote the `G15` text, one unit off in the 15th digit for a few percent of doubles with more digits.
- The fixture has a sixteenth site, `Funding/BorrowInterest.cs`, hourly interest at `(decimal)(1.0 / 8760)`, and a 31st test that pins its .NET 10 amount, `13.69863013698624`.
- .NET 10 gave the fraction `0.000114155251141552`, while `G15` gives `…553`, so the test fails with the 1.3.0 fix, with the `G15` helper, with `1m / 8760` and with the plain cast.

The graders, prompts and settings are otherwise those of [the last run](2026-10-27-dotnet-format-sonnet-5.5.md), so the scores compare directly apart from the new site.

## Reading

The scores repeat the last run's within a few hundredths, with the same mean Δ, so the two skill changes since then cost nothing measurable.
Every skill run that changed code left the edits to `dotnet format`, and every skill run kept every site the fixture keeps and put the build files back.

The new site shows where the analyzer pays beyond keeping casts.
Its correct value is not the obvious one: the documented recipe, the exact decimal `1m / 8760` and the plain cast all fail its test.
No skill run had to work it out, since the fix writes the right literal.
The baseline found it through the failing test, and in two runs spent about $0.30 more porting .NET 10's conversion, which is why its `migrate` and `migrate-full` runs cost $0.39 and $0.34 where the last run's cost $0.23 and $0.31.
Every baseline run ended right, so the tests alone would have caught a wrong literal; the cost is the time it takes to find the right one.

Three of twelve skill runs still printed a whole C# file with `cat`, as in the last run, and five of twelve ran a grep over the sources or tests, two more than then, against six of twelve without the skill.
No run of either arm used the Grep tool or read a whole C# file with the Read tool.

Two `migrate-full` skill runs noted in their report that the helper cuts a computed double to 15 significant digits, so its result is not exactly .NET 10's for those values.
That is the limit the README now states: `G15` matches .NET 10 for a value written with up to 15 significant digits, and can differ by one unit in the 15th digit for a computed one.

## Limits

- One fixture, small enough that reading every file is cheaper than the listing; a larger fixture is needed to measure the savings.
- In the sandbox `dotnet format` is a stand-in; it matched the real one byte for byte on this fixture, kept and converted, but has not been compared on other solutions.
- The trace graders match the command text, so an unusual search or read could pass them.
- One model, 3 runs per arm: enough to see a consistent pattern, not to put a confidence interval on it.
